## 검수를 건너뛰면 일이 커진다

웹사이트를 완성하면 검수 작업을 하게 됩니다. 이때 검수를 소홀히 하거나 아예 건너뛰면 오픈한 뒤에 문제가 터지고 그때는 고치는 일보다 수습하는 일이 더 커집니다. 그래서 꼼꼼한 검수는 빠뜨릴 수 없는 과정입니다.

이 글은 처음 웹 퍼블리셔로 일하게 될 분들께 제가 실제로 검수할 때 보는 것들을 순서대로 정리한 것입니다. 기본 세 단계를 먼저 보고 그다음 놓치기 쉬운 항목들을 따로 다룹니다.

검수에서 가장 중요한 건 당연하게도 눈에 보이는 화면입니다. 그래서 첫 단계도 화면부터 시작합니다.

## 1. 해상도별 화면 검수

요즘은 반응형으로 만들어서 소스 하나로 PC, 태블릿, 모바일을 모두 쓰는 경우가 대부분입니다. 그만큼 화면 크기가 바뀌는 사이에 깨지는 UI는 없는지, 글자 크기는 적당한지 확인해야 합니다.

작은 폰에서도 보고 폴더블처럼 넓은 폰에서도 봐야 합니다. 요즘은 모바일 중심으로 작업하는 일이 많은데 모바일 기기 안에서도 해상도가 제각각이기 때문입니다.

| 확인할 것 | 보는 방법 |
|---|---|
| 가장 좁은 화면 | 개발자도구에서 가로 320px까지 줄여 봅니다. 가로 스크롤이 생기거나 글자가 잘리면 안 됩니다 |
| 넓은 폰·태블릿 | 폴더블을 펼친 화면, 태블릿 세로·가로를 모두 봅니다. 모바일 레이아웃이 어색하게 늘어나는 구간이 잘 생깁니다 |
| 화면이 바뀌는 경계 | 미디어 쿼리 기준값 바로 앞뒤에서 레이아웃이 튀지 않는지 봅니다 |
| 글자 크기 | 모바일 본문이 너무 작지 않은지, 브라우저 글자 크기 설정을 키웠을 때 깨지지 않는지 봅니다 ([px와 rem 기초](/blog/px-rem-basics/)) |

그리고 **브라우저의 모바일 모드로 본 결과와 실제 폰의 모바일 웹, 앱에서 본 결과가 다를 때가 있습니다.** 개발자도구의 모바일 모드는 화면 크기를 흉내 낼 뿐 그리는 건 여전히 PC 크롬입니다. 아이폰에서는 크롬 앱도 대부분 사파리와 같은 WebKit 엔진으로 그리기 때문에 PC에서 본 모습과 차이가 날 수 있습니다. 흔한 예가 `height: 100vh`입니다. 실제 폰에서는 주소창 높이 때문에 화면 아래가 잘리는데 개발자도구에서는 이 차이가 보이지 않습니다. 이런 곳은 `100dvh`처럼 주소창을 반영하는 단위로 바꿔 줍니다. 개발자도구 확인이 끝나면 반드시 실제 기기로 한 번 더 봅니다.

## 2. 디자이너와 함께하는 디자인 검수

화면 검수가 끝나면 디자이너에게도 확인할 수 있는 링크를 주고 함께 검수합니다. 대부분은 시안을 보면서 만들었기 때문에 크게 다른 건 없을 겁니다. 그런데 디자이너가 실제로 돌아가는 홈페이지를 보고 나서 바꾸고 싶은 부분이 생기는 일이 많습니다. 시안 이미지로 볼 때와 브라우저에서 스크롤하며 볼 때 느낌이 다르기 때문입니다.

이 단계에서 특히 같이 봐야 하는 건 **움직이는 부분**입니다. 애니메이션, 화면 전환, 메뉴가 열리는 속도처럼 시안 이미지에는 담기지 않는 동작이 디자이너가 생각했던 것과 같은지 확인합니다.

저도 디자이너가 요구한 대로 애니메이션을 만들었는데 실제로 써 보니 너무 느려서 디자이너가 더 빠르게 바꿔 달라고 한 적이 있습니다. 시안과 설명만으로는 알기 어렵고 직접 눌러 봐야 드러나는 부분입니다. 그래서 움직임은 디자이너가 실제 화면에서 써 보게 하는 게 좋습니다.

수정 요청은 링크와 함께 캡처나 목록으로 받아 두면 좋습니다. 말로만 주고받으면 어떤 페이지의 어느 부분 이야기였는지 나중에 헷갈립니다.

## 3. 동작 확인

스크립트나 PHP 코드처럼 실제 사이트 운영에 관한 코드가 제대로 도는지 확인하는 단계입니다. 개발자와 함께 작업했다면 이 단계는 개발자와 함께 테스트합니다.

이 과정에서 버그를 잡아내는 게 정말 중요합니다. 올바른 방법으로만 써 보지 말고 **일부러 잘못된 방법으로도 실행해 보면서** 어떻게 반응하는지 봐야 합니다. 실제로 개발하다 보면 어떤 식으로든 생각하지 못한 버그가 많이 생기기 때문입니다.

| 일부러 해 볼 것 | 걸리는 문제 |
|---|---|
| 필수 칸을 비우고 제출 | 안내 문구 없이 그냥 넘어가거나 빈 값이 저장된다 |
| 제출 버튼을 여러 번 빠르게 누르기 | 같은 글이나 신청이 두 번 들어간다 |
| 아주 긴 글자, 띄어쓰기 없는 영문 입력 | 칸 밖으로 넘치거나 레이아웃이 깨진다 |
| 따옴표·꺾쇠 같은 특수문자 입력 | 저장이 안 되거나 화면에 이상하게 나온다 |
| 로그인 상태와 비로그인 상태 둘 다 | 한쪽에서만 메뉴나 버튼이 보이지 않는다 |
| 개발자도구 Network 탭에서 속도를 3G로 낮추기 | 로딩 중에 버튼이 눌리거나 빈 화면이 오래 보인다 |

저는 문자 인증 과정을 검수하면서 일부러 인증번호를 틀리게 넣어 보고 제한 시간이 지날 때까지 기다려 보기도 했습니다. 그러다 서버에서 보내 주는 에러 메시지가 잘못 나오는 걸 발견한 적이 있습니다. 순서대로만 눌러 봤다면 오픈한 뒤에 사용자가 먼저 겪었을 문제입니다.

## 기본으로 같이 보는 것: 오타, 이미지, 링크

위 세 단계를 거치면서 기본으로 같이 챙기는 것들입니다. 따로 시간을 잡기보다 화면을 볼 때마다 함께 봅니다.

- **오타** — 메뉴명, 버튼 문구, 푸터의 회사 정보와 전화번호까지 봅니다. 푸터는 모든 페이지에 들어가서 틀리면 전부 틀립니다
- **이미지 크기** — 용량이 너무 크지 않은지, 흐리게 늘어난 이미지는 없는지 봅니다 ([웹 이미지 실전](/blog/image-practical/))
- **링크** — 메뉴, 버튼, 푸터 링크를 하나씩 눌러 봅니다. 작업 중에 임시로 넣어 둔 `href="#"`이 남아 있지 않은지도 검색해 봅니다

## 놓치기 쉬운 항목들

기본 세 단계 말고도 프로젝트에 따라 꼭 따로 봐야 하는 것들이 있습니다.

### 브라우저에 따른 차이

요즘은 PC에서 크롬, 웨일, 엣지, 사파리를 쓰고 모바일에서는 여기에 삼성 인터넷 정도가 더해집니다. 이 브라우저들은 최신 CSS를 대부분 잘 지원해서 크게 문제 될 일이 없습니다.

문제는 **인터넷 익스플로러(IE)** 입니다. 마이크로소프트는 2022년 6월에 IE 지원을 끝냈지만 예전 컴퓨터나 일부 기관의 내부망에서는 아직 IE나 엣지의 IE 모드로 사이트를 여는 곳이 있습니다. IE는 지원이 끝난 지 오래라 보안에 취약하고 CSS 변수, 화살표 함수 같은 최신 문법을 지원하지 않습니다.

그래서 IE에서 써야 하는 사이트라면 코드를 처음부터 IE에서도 돌아가게 작업해야 합니다. 이건 검수 때가 아니라 **작업을 시작하기 전에** 확인할 일입니다. 다 만든 뒤에 IE 대응이 필요하다는 걸 알면 거의 새로 짜야 하기 때문입니다. 공공기관 프로젝트라면 기획서나 작업지시서에 지원 브라우저가 적혀 있는지부터 확인하세요.

저도 크롬과 엣지에서 아무 문제가 없는 걸 확인하고 제작 완료를 전달한 적이 있습니다. 그런데 사용자가 엣지의 IE 모드로 열었더니 에러가 난다고 했습니다. 결국 IE 모드에서 직접 확인하면서 다시 작업했는데 에러가 어디서 나는지 찾기도 힘들어서 고생했습니다.

IE 모드로 연 탭은 F12를 눌러도 평소 쓰는 엣지 개발자도구로 확인할 수 없습니다. 윈도우에 들어 있는 IEChooser(`C:\Windows\System32\F12\IEChooser.exe`)를 실행하고 IE 모드 탭을 골라야 IE용 개발자도구가 열립니다.

### 앱, 웹앱, iOS, 안드로이드에 따른 차이

모바일 위주로 작업하는 일이 많아지면서 휴대폰으로 확인하는 과정도 많아졌습니다. 이때 폰의 운영체제와 함께 **내가 만든 페이지가 어디서 열리는지**에 따라 동작을 따로 테스트해야 합니다. 같은 페이지라도 모바일 브라우저에서 열 때와 앱 안의 웹뷰에서 열 때가 다릅니다.

저도 이 차이를 겪었습니다. PC 웹과 모바일 웹에서는 아무 문제가 없던 동작이 웹뷰로 만든 앱에서 열었을 때는 제대로 되지 않았습니다. 링크를 눌러도 이동이 안 되는 식이었습니다. 나중에 확인해 보니 앱 코드 자체에서 따로 설정해 줘야 하는 기능들이 있었습니다. 그래서 앱 제작자와 외부 링크 이동과 권한 설정 등을 두고 회의를 했습니다.

웹뷰에서 자주 막히는 것들은 이렇습니다. 앱에서 열리는 페이지라면 이 목록을 들고 앱 제작자와 미리 이야기해 두면 좋습니다.

| 기능 | 웹뷰에서 생기는 일 |
|---|---|
| `target="_blank"` 링크, 외부 링크 | 아무 반응이 없거나 앱 안에서 열려서 돌아올 방법이 없다 |
| 파일 첨부(`<input type="file">`) | 앱에서 처리해 주지 않으면 눌러도 파일 선택 창이 뜨지 않는다 |
| 카메라, 위치 정보 | 앱에 권한 설정이 없으면 동작하지 않는다 |
| 전화(`tel:`), 문자, 지도 앱 연결 | 앱이 다른 앱으로 넘겨주지 않으면 열리지 않는다 |

### 메타태그·OG

화면에는 보이지 않지만 검색 노출(SEO)과 링크를 공유할 때 나오는 문구, 이미지를 정하는 부분입니다. 메타태그, 파비콘, OG를 제대로 넣어서 내 결과물이 사람들에게 보이도록 해야 합니다. 웹사이트를 다 만들었는데 검색에 나오지 않으면 그동안의 노력이 물거품이 되기 쉽습니다.

검수할 때는 이 세 가지를 봅니다.

- 페이지마다 `title`과 `description`이 다르게 들어가 있는지
- 카카오톡이나 메신저에 링크를 붙여 넣었을 때 미리보기 이미지와 문구가 나오는지
- 개발 서버에서 검색을 막으려고 넣어 둔 `<meta name="robots" content="noindex">`가 그대로 남아 있지 않은지. 이게 남아 있으면 오픈해도 검색에 나오지 않습니다

작성법과 미리보기가 안 뜰 때 확인할 것은 [메타태그와 Open Graph 정리](/blog/seo-meta-tags-and-open-graph/)에 따로 정리해 두었습니다.

### 웹 접근성

기본적인 웹 접근성은 다들 챙기겠지만 공공기관 사이트이거나 웹 접근성 인증을 받아야 하는 사이트라면 훨씬 꼼꼼히 봐야 합니다. 키보드만으로 모든 동작이 되는지, 대체 텍스트는 다 들어가 있는지, 스크린 리더로 읽을 때 문제는 없는지 등 확인할 부분이 많습니다.

신입 때 가장 흔한 실수는 `img` 태그에 `alt`를 넣지 않는 것입니다. 사소해 보여도 이런 하나가 접근성에 영향을 줍니다. `alt`가 없으면 스크린 리더가 파일 이름을 그대로 읽기도 합니다. 꾸밈용 이미지라 읽을 필요가 없다면 `alt`를 빼는 대신 `alt=""`처럼 빈 값을 넣어 건너뛰게 합니다.

또 하나는 탭 메뉴를 `div`로 만드는 경우입니다. `div`는 키보드 포커스를 받지 못해서 Tab 키로 탭 메뉴에 들어가지 못하는 상황이 생깁니다. 누르는 요소는 `button`으로 만드는 게 기본입니다.

```html
<!-- ✗ 키보드로 갈 수 없다 -->
<div class="tab" onclick="showTab(1)">공지사항</div>

<!-- ○ Tab 키로 이동하고 Enter·Space로 누를 수 있다 -->
<button type="button" class="tab" onclick="showTab(1)">공지사항</button>
```

검수 때는 마우스를 내려놓고 Tab 키만으로 페이지 끝까지 가 보는 것이 가장 빠른 확인 방법입니다. 지금 어디에 포커스가 있는지 눈에 보이는지도 함께 봅니다. 글자와 배경의 대비는 [색 대비 실무](/blog/wcag-contrast-practical/)에서 확인 방법을 다뤘습니다.

### 팝업과 뒤로가기

PC에서는 팝업을 다루기가 꽤 쉽습니다. 모바일로 넘어가면 신경 쓸 것이 많아집니다. 특히 앱에서 팝업이 뜨면 사용자는 X 버튼 대신 뒤로가기 버튼이나 제스처로 팝업을 닫으려고 합니다. 이때 뒤로가기에 팝업이 닫히도록 되어 있지 않으면 사용자는 원하지 않게 이전 페이지로 가 버립니다.

그래서 앱에서 팝업을 다룰 때는 팝업을 열 때 가상 히스토리를 하나 쌓아 두고 뒤로가기가 들어오면 팝업만 닫는 식으로 처리해야 합니다. 검수 때는 팝업과 사이드메뉴를 열어 두고 실제 폰에서 뒤로가기를 한 번씩 눌러 봅니다. 코드는 [사이드메뉴 제작법의 뒤로가기 항목](/blog/practice-sidemenu/)에 있고 팝업에도 같은 방식을 쓰면 됩니다([팝업 제작법](/blog/practice-popup/)).
