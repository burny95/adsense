## 지금 돌아가는 사이트를 고친다는 부담

처음 유지보수를 맡았을 때 가장 크게 다가온 건 부담감이었습니다. 남이 만들어 놓은 코드를, 그것도 지금 실제로 돌아가고 있는 사이트나 프로그램의 코드를 고쳐야 했으니까요. 잘못 건드리면 지금 누군가 보고 있는 화면이 그대로 깨집니다.

신입 퍼블리셔가 처음 맡는 일도 새 사이트를 만드는 것보다 이런 유지보수인 경우가 많습니다. 버튼 색 바꾸기, 배너 교체, 문구 수정, 모바일에서 깨지는 곳 잡기 같은 일들입니다.

이 글은 처음 웹 퍼블리셔로 일하게 될 분들께 제 경험을 바탕으로 유지보수를 어떻게 하면 좋은지 정리한 것입니다.

## 1. 백업은 철저히

유지보수에서 가장 중요한 작업은 백업입니다. 작업을 시작하기 전에는 항상 백업부터 하세요.

코드 수정은 어떤 일이 생길지 모릅니다. 문법과 코드 규칙에 맞게 썼더라도 운영체제, 브라우저 종류와 버전, PHP 버전처럼 수많은 변수가 기다리고 있기 때문입니다. 아무리 올바른 코드를 써도 이전 코드와 충돌이 나거나 클래스 이름이 겹치거나 스크립트가 동작하지 않는 일이 생깁니다. 그러니 언제든 되돌아갈 수 있게 백업하는 습관을 들이는 게 좋습니다.

- 고치기 전 파일을 복사해 둡니다. git을 쓰는 프로젝트라면 수정 전에 커밋해 둡니다.
- 무엇을 고쳤는지 짧게 적어 둡니다. 날짜, 페이지, 바꾼 내용 정도면 충분합니다. 몇 달 뒤 비슷한 요청이 왔을 때 그때 어떻게 고쳤는지 바로 찾을 수 있습니다.

## 2. 기존 구조를 활용하기

회사에 들어가 이전 작업자가 만든 코드나 오래된 홈페이지, 오래된 프로그램의 코드를 보면 왜 이렇게 복잡하고 비효율적으로 짰는지 이해가 안 갈 때가 많습니다. 그래도 새 구조로 바꿔서 효율적으로 만들어야겠다는 생각은 내려놓는 게 좋습니다.

유지보수에서 가장 중요한 건 안정성입니다. 지금 돌아가는 웹이나 앱, 프로그램에 어떤 오류도 나서는 안 됩니다. 그래서 지금 작성된 코드를 기반으로 에러 가능성을 최대한 줄여 작업하는 것이 가장 좋은 방법입니다.

구조를 바꾸는 건 때가 따로 있습니다. 구조 자체가 달라지거나 콘텐츠가 많이 늘어 작업량이 커지고 새 관리 시스템을 들여야 할 정도가 됐을 때입니다. 그때 구조 변경을 권합니다.

## 3. 요청자의 의도부터 이해하기

수정 요청은 회사 안에서 올 때도 있고 외부 클라이언트가 직접 연락해 올 때도 있습니다. 어느 쪽이든 요청자의 의도를 잘 파악하고 작업해야 합니다. 그렇지 않으면 메일과 전화가 여러 번 오가고 간단한 작업에 많은 시간을 쓰게 됩니다.

처음 수정 사항을 들었을 때 헷갈리는 부분이 있거나 기술적으로 불가능하거나 바꿨을 때 우려되는 점이 보이면 바로 요청자와 이야기하세요. 작업에 들어가기 전에 업무를 제대로 이해해야 나와 요청자 모두 만족하는 수정이 됩니다.

요청은 대개 "메인 버튼이 이상해요", "모바일에서 깨져요"처럼 짧게 옵니다. 작업 전에 아래 네 가지는 확인해 두면 다시 묻는 횟수가 줄어듭니다.

| 확인할 것 | 이유 |
|---|---|
| 어느 페이지인가 (주소) | 같은 버튼이 여러 페이지에 있으면 어느 쪽인지 모른다 |
| 어떤 기기·브라우저인가 | 아이폰 사파리에서만 깨지는 경우가 흔하다 |
| 화면 캡처 | "이상하다"의 뜻이 사람마다 다르다 |
| 언제부터인가 | 최근 수정 때문인지, 원래 그랬는지 가를 수 있다 |

## 4. 새 클래스를 추가해서 작업하기

실제로 작업할 때 주의할 점입니다. 대부분의 경우 클래스 이름이 붙은 태그들은 이미 사이트 곳곳에서 쓰이고 있습니다. 이런 태그를 그대로 가져다 쓰면 기존 CSS와 충돌이 나기 쉽습니다.

그래서 새로운 형식이나 스타일, 구조를 쓸 때는 기존 CSS에 덧붙이기보다 **새 클래스를 추가해서 그 클래스만의 CSS를 작업하는 편**이 더 안정적이고 이후 유지보수에도 좋습니다. 소스는 몇 줄 길어지지만 안정성이 크게 올라가고 기존 디자인도 그대로라서 원하는 곳만 핀포인트로 고칠 수 있습니다.

### 먼저 고칠 곳과 영향 범위를 찾는다

남이 만든 사이트는 구조를 모르는 상태에서 시작합니다. 파일을 하나씩 열어 보는 것보다 화면에서 거꾸로 찾아 들어가는 쪽이 빠릅니다.

1. 크롬에서 `F12`로 개발자도구를 열고 `Ctrl + Shift + C`를 누른 뒤 고칠 요소를 클릭합니다.
2. 오른쪽 Styles 패널에 그 요소에 걸린 CSS가 나옵니다. 규칙마다 `common.css:120`처럼 파일 이름과 줄 번호가 붙어 있습니다. 줄이 그어진 규칙은 다른 규칙에 덮여 적용되지 않는 것입니다.
3. VS Code라면 `Ctrl + Shift + F`로 프로젝트 전체에서 그 클래스 이름을 검색합니다. 여기서 나온 개수가 이 수정이 영향을 주는 범위입니다. 다만 게시판 글처럼 관리자 화면에서 입력한 내용이나 스크립트가 나중에 붙이는 클래스는 파일 검색에 걸리지 않으니 그런 곳이 있는지도 함께 봅니다.

### 예: 버튼 하나만 색을 바꿀 때

이벤트 페이지 버튼 하나만 빨간색으로 바꿔 달라는 요청을 받았다고 합시다. 버튼에 걸린 규칙은 이렇습니다.

```css
/* common.css — 사이트 전체 버튼 */
.btn {
  padding: 12px 24px;
  background: #333;
  color: #fff;
}
```

여기서 `background`를 바꾸면 사이트의 모든 버튼이 같이 빨개집니다. 공통 규칙은 그대로 두고 바꿀 버튼에만 클래스를 하나 더 붙입니다.

```html
<a href="/event/" class="btn btn--event">이벤트 참여하기</a>
```

```css
/* 이벤트 버튼만 */
.btn--event {
  background: #c62828;
}
```

`.btn`의 여백과 글자색은 그대로 받고 배경만 바뀝니다. 다른 페이지 버튼에는 `btn--event`가 없으니 영향이 없습니다.

## 5. !important가 걸려 있을 때

`!important`는 그 선언을 가장 우선으로 적용하라는 표시입니다. 기존 CSS에 이게 붙어 있으면 내가 쓴 선택자가 아무리 구체적이어도 반영되지 않습니다.

이런 곳을 고쳐야 한다면 내 쪽에도 `!important`를 붙이고 선택자 우선순위를 기존보다 높입니다. `!important`끼리 부딪히면 우선순위가 높은 선택자가 이기기 때문입니다. 우선순위는 앞에 id나 클래스를 더 붙여서 올립니다.

```css
/* 기존 */
.notice .title { color: #333 !important; }

/* 덮어쓰기 — 이벤트 영역(id="event") 안에서만, 앞에 id를 붙여 우선순위를 올린다 */
#event .notice .title { color: #c62828 !important; }
```

이때 `>`(직계 자식 선택자)는 우선순위를 올려 주지 않습니다. 선택 범위를 좁힐 뿐이고 우선순위는 id, 클래스(속성·가상 클래스 포함), 태그가 몇 개인지로만 정해집니다. `.notice > .title`과 `.notice .title`은 우선순위가 같습니다.

그래도 안 되면 태그에 직접 `style="color: #c62828 !important;"`처럼 써 넣습니다. 인라인 스타일에 붙인 `!important`는 CSS 파일의 `!important`보다 우선합니다. 다만 이렇게 넣은 값은 다음 사람이 CSS 파일에서 찾을 수 없으니 마지막 방법으로만 씁니다.

## 6. 확인 작업은 캐시까지

대부분의 요청자는 컴퓨터나 웹 전문가가 아닙니다. 수정을 마쳤다고 알려도 아무 의심 없이 그냥 사이트에 들어가거나 일반 새로고침으로 확인합니다. 그러면 브라우저가 예전에 받아 둔 CSS를 그대로 써서 "수정한 게 안 보여요"라는 말을 자주 듣게 됩니다.

방법은 세 가지입니다.

**CSS 주소에 버전을 붙인다.** 버전이나 날짜를 쿼리스트링으로 붙여 둡니다.

```html
<link rel="stylesheet" href="style.css?v=1.0.1">
```

`?v=` 뒤 값이 바뀌면 브라우저는 다른 파일로 보고 새로 받아 옵니다. 요청자가 따로 할 일이 없어서 가장 확실합니다. 고칠 때마다 값을 바꿔 주세요.

**강력 새로고침을 미리 알려 준다.** `Ctrl + F5` 또는 `Ctrl + Shift + R`(맥은 `Cmd + Shift + R`)을 알려 주고 그걸로 확인해 달라고 합니다. 핸드폰에는 이런 단축키가 없어서 모바일로 확인하는 요청자에게는 버전을 붙이는 쪽이 확실합니다.

**작업하는 동안은 내 브라우저 캐시를 끈다.** 개발자도구 Network 탭에서 **Disable cache**를 켜 두면 개발자도구가 열려 있는 동안은 캐시를 쓰지 않습니다. 고칠 때마다 강력 새로고침을 누르지 않아도 됩니다.

캐시 확인이 끝나면 범위를 넓혀서 봅니다.

1. **고친 페이지** — PC와 모바일 둘 다
2. **같은 클래스를 쓰는 다른 페이지** — 4번에서 검색으로 찾은 곳들
3. **요청에 적힌 기기·브라우저** — 아이폰 사파리에서 깨진다는 요청이었다면 거기서 다시 봅니다

마지막으로 요청자에게 **수정 전후 캡처**를 함께 보내면 "고쳤습니다"라는 말만 보낼 때보다 오해가 훨씬 적습니다.

## 요약

- 작업 전에는 항상 백업한다. 무엇을 고쳤는지도 적어 둔다
- 오래된 코드가 비효율적이어도 구조는 그대로 두고 안정성을 우선한다. 구조 변경은 작업량이 커지고 관리 시스템을 바꿀 때
- 요청이 헷갈리거나 불가능하거나 우려되는 점이 있으면 작업 전에 바로 묻는다
- 기존 클래스를 고치지 말고 새 클래스를 추가해서 작업한다
- `!important`를 덮으려면 내 쪽도 `!important` + 더 높은 우선순위로. `>`는 우선순위를 올리지 않는다
- 고친 뒤에는 CSS 주소에 `?v=` 버전을 붙여 캐시 문제를 막고 같은 클래스를 쓰는 페이지까지 확인한다
